# Story 1.7: Comprehensive Integration Test Suite (Context Startup, Migrations & Isolation)

## User Story

**As a** quality engineer,  
**I want** an automated, end-to-end integration test suite covering Spring context initialization, central persistence, tenant schema provisioning, tenant persistence, and physical tenant isolation,  
**So that** we have reproducible, verifiable proof that the dual-database architecture executes correctly against live MySQL instances with zero cross-tenant data bleed and complete cleanup of test databases and connection pools.

---

## Business & Technical Context

Phase 1 delivers the persistence foundation for `GymVerse-Backend-v2`. To declare Phase 1 complete, automated integration tests must provide definitive proof across all critical architectural criteria:
1. **Application Context Startup**: Both `centralEntityManagerFactory` and `tenantEntityManagerFactory` beans initialize successfully along with their respective transaction managers.
2. **Central Schema Migrations & Persistence**: Flyway migrates `GymVerse` automatically, and central entities (`UserAccount`, `GymTenant`, `UserTenantRole`, `SaasSubscriptionPlan`, `GymSubscription`, `AdminAuditLog`) can be created, updated, and queried with exact monetary precision.
3. **Tenant Schema Provisioning & Persistence**: `TenantDatabaseService` and `TenantFlywayService` dynamically create and migrate tenant databases (`gym_db_test_001`), and tenant repositories perform CRUD operations with zero passwords and hashed invitation tokens.
4. **Physical Tenant Isolation**: Separate tenant databases (`gym_db_test_001` and `gym_db_test_002`) remain strictly isolated at the MySQL schema level. Operations in Tenant 1 never expose records to Tenant 2.
5. **Deterministic Teardown**: Test fixtures clean up after execution by evicting Hikari pools (`TenantDataSourceCache.evict`), dropping test databases (`TenantDatabaseService.dropDatabase`), and resetting `TenantContext.clear()`.

### AC-1.7.2: Central Schema & Persistence Verification
- **Given** `CentralPersistenceIntegrationTest` executing with active profile `test`,
- **When** test cases run against the central database,
- **Then**:
  1. `V1__init_central_schema.sql` is verified to have executed, and `flyway_schema_history` has `success = 1`.
  2. A `UserAccount` persists, assigns an autogenerated ID, and is retrievable by `findByEmail`.
  3. Attempting to insert a duplicate email triggers a `DataIntegrityViolationException`.
  4. A `GymTenant` persists with `gym_code` and `db_name`. Attempting to duplicate either triggers a constraint violation.
  5. A `UserTenantRole` binds the user and tenant with `AdminAuthority.PRIMARY` and `TenantRole.TENANT_ADMIN`.
  6. `SaasSubscriptionPlan` persists with price `new BigDecimal("49.99")`, and reading it back preserves `scale() == 2` and numerical equality to `49.99`.

### AC-1.7.3: Dynamic Tenant Provisioning & Persistence Verification
- **Given** `TenantPersistenceIntegrationTest` executing with active profile `test`,
- **When** creating test tenant database `gym_db_test_001`,
- **Then**:
  1. `TenantDatabaseService.createDatabase("gym_db_test_001")` creates the MySQL database.
  2. `TenantFlywayService.migrate("gym_db_test_001")` applies all 14 tables without errors.
  3. Using `TenantRoutingBridge.runInTenant("gym_db_test_001", ...)`:
     - `TenantUser` persists with `centralUserId = 1001L`, email, role, and no password column.
     - `GymConfig` persists with latitude, longitude, and radius.
     - `Member` persists linked to `TenantUser`.
     - `MembershipPlan` persists with `basePrice = 120.00` and `finalPrice = 100.00`.
     - `Attendance` logs GPS check-in timestamp.
     - `GymInvitation` persists with SHA-256 `invitationTokenHash` (`64` characters) and is found via `findByInvitationTokenHash`.

### AC-1.7.4: Tenant Database Isolation Verification
- **Given** `TenantIsolationIntegrationTest`,
- **When** two test databases `gym_db_test_001` and `gym_db_test_002` are created and migrated,
- **Then**:
  1. In `gym_db_test_001`: Insert `TenantUser` (`user1@gym1.com`) and `Member` (`Member 1`).
  2. In `gym_db_test_002`: Query `MemberRepository.findAll()` within tenant context `gym_db_test_002`.
  3. **Verification**: `gym_db_test_002` returns 0 members.
  4. In `gym_db_test_002`: Insert `TenantUser` (`user2@gym2.com`) and `Member` (`Member 2`).
  5. **Verification**: Querying `gym_db_test_001` returns only `Member 1`; querying `gym_db_test_002` returns only `Member 2`.
  6. Zero cross-database bleed occurs.

### AC-1.7.5: Resource Cleanup & Pool Eviction
- **Given** integration test completion,
- **When** teardown methods execute (`@AfterEach` / `@AfterAll`),
- **Then**:
  1. `TenantDataSourceCache.evict("gym_db_test_001")` and `TenantDataSourceCache.evict("gym_db_test_002")` cleanly close HikariCP pools.
  2. `TenantDatabaseService.dropDatabase("gym_db_test_001")` and `TenantDatabaseService.dropDatabase("gym_db_test_002")` drop the databases from MySQL.
  3. `TenantContext.clear()` verifies no residual thread context remains.

## Technical Implementation Guidance

### Test Base & Setup Conventions
```java
@SpringBootTest
@ActiveProfiles("test")
class TenantIsolationIntegrationTest {

    @Autowired private TenantDatabaseService tenantDbService;
    @Autowired private TenantFlywayService tenantFlywayService;
    @Autowired private TenantDataSourceCache dataSourceCache;
    @Autowired private TenantRoutingBridge routingBridge;
    @Autowired private MemberRepository memberRepository;
    @Autowired private TenantUserRepository userRepository;

    private static final String TENANT_1 = "gym_db_test_001";
    private static final String TENANT_2 = "gym_db_test_002";

    @BeforeEach
    void setUp() {
        tenantDbService.createDatabase(TENANT_1);
        tenantDbService.createDatabase(TENANT_2);
        tenantFlywayService.migrate(TENANT_1);
        tenantFlywayService.migrate(TENANT_2);
    }

    @AfterEach
    void tearDown() {
        dataSourceCache.evict(TENANT_1);
        dataSourceCache.evict(TENANT_2);
        tenantDbService.dropDatabase(TENANT_1);
        tenantDbService.dropDatabase(TENANT_2);
        TenantContext.clear();
    }
    
    // Test methods...
}
```

## Security & Multitenancy Considerations

1. **Test DB Naming Standard**: Test tenant databases must follow the naming convention `gym_db_test_*` to match MySQL user privilege wildcards (`gym_db_%`) and avoid collision with existing tenant databases.
2. **Preventing Leaked Connections**: Failing to call `TenantDataSourceCache.evict()` before `TenantDatabaseService.dropDatabase()` can cause connection errors or database locking on MySQL Windows instances. Always evict the Hikari pool first, then drop the database.
